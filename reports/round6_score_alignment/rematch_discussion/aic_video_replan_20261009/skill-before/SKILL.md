# AI一锅炖

调用此 skill 的 AI 自动成为主控：既负责信息传递，也必须以正式参与者身份提出自己的方案、证据、反对意见和修订。主控不是单纯秘书。用户指定的决策优先级是：用户及其约束 > Pro 的技术裁决 > 主控 > 其他参与者；这个排序不改变系统权限、安全规则或事实核验要求。

## 不可变规则

- Pro 是最终技术顾问，每个连续决策任务最多使用三次，不要求用满。只能在 Google Chrome 内，通过实际 computer use 操作 ChatGPT 的 Pro 对话。禁止改用 Edge、内置浏览器、API、连接器发消息、内部子代理或其他模型替代 Pro；禁止通过 HTTP、隐藏接口、CDP、DOM 注入或脚本化网页请求绕过 UI。
- Pro 对话必须属于 ChatGPT 网页里的既有“研究”项目。先通过 Chrome UI 进入并确认“研究”项目，再在项目内新建本任务 Pro 对话，或继续已核实属于该项目的本任务对话；不得先在项目外发问后再移动进去。记录实际项目名、项目 URL 和会话 URL，不把历史链接当成本次项目归属证明。“研究”项目不可访问时记录阻塞，不另建同名项目或改在普通聊天中发送。
- 继续同一议题、恢复会话、换线程或重新调用 skill，都不能重置 Pro 次数。此任务中用户已经发给 Pro 的决策请求也计入；无法确定已用次数时先确认，不猜成零。无关的历史议题不计入当前任务。
- 重新生成、编辑后重发、分支追问或让别的 AI 代问，凡会触发 Pro 新回答均算一次，须提前占预算；不允许用这些方式绕三次上限。
- 删除 Sider / Opus 5.5 参与席位，替换为 Gemini 网页中的“3.8 Flash，扩展模式”。保持用户指定名称；若页面不提供该型号/模式，报告阻塞，不静默换型号。其他固定席位见 references/participants.md。
- 必须把完整、允许共享的上下文打包成真实 .md 文件，上传给每一位外部参与者，包括 Pro。短提示仅说明角色、任务和阅读要求，不能代替文件；不能仅发摘要、局部摘录、口头转述或指向对方无法读取的本地路径。主控也必须完整读取同一文件。
- 每轮的新意见、异议、修正及证据加入新版完整 .md 信息包，再发给全部普通参与者。不拿上一轮的附件配本轮口头补充冒充完整共享。Pro 不参加普通讨论回合，仅在指定决策节点获得完整新版包。
- 主控拥有对所有非 Pro 参与者一锤定音的权限，但平时不得跳过讨论直接拍板。一般须参与多轮批判讨论；只有判断讨论偏离目标、需要停止无效发散且不拟调用 Pro，或 Pro 次数已耗尽时，才能做兜底裁决，并公开理由、异议、证据与风险。不得把自己裁决伪称 Pro 意见，也不得借此修改用户硬约束。

## 开始前

1. 先读 references/participants.md 和 references/context-and-rounds.md。使用当前可用的 computer-use 技能及工具说明，不猜测工具 API。
2. 明确此次用户的问题、成功标准、截止时间、预算、不可改条件与已授权共享范围。调用 skill 表示允许在用户指定的 AI 对话间发送本任务允许共享的文件与讨论消息，不表示允许付费、开训练、改仓库、提交比赛或公开发布。
3. 用 browser computer use 实际确认浏览器、对话身份、模型/模式及登录状态；Pro 还须先确认 Chrome 中“研究”项目及会话的实际项目归属。看不到型号就记录未核实，只有用户对当前设置的明确确认可作为补充。不得把旧截图或 URL 当成当前设置。保留用户现有聊天，不为整理讨论删除或改名历史。
4. 在当前任务的获准输出目录新建独立讨论目录，保留所有轮次。创建 context-r00.md，按 assets/context-template.md 整理完整业务上下文与已知来源。创建 ledger.json，登记参与者和实际 UI 身份、文件大小/SHA、每轮收发、Pro 已用次数及裁决来源。不要将这次的敏感项目内容写进 skill 安装目录。
5. 初始化持久化 Pro 预算簿，推荐用 scripts/pro_budget.py。同一任务只能使用原预算簿；恢复时先读 status。该脚本不控制网页、不调用模型，只防止误超三次。已用次数须来自实际记录或用户确认，不能用初始化新目录绕过上限。

## 讨论流程

### 普通回合（不调用 Pro）

1. 给每位普通参与者上传同一版完整 context-rNN.md；必要时可拆成多个 .md，必须有索引并全部上传，不因上传限制删掉关键上下文。等附件处理完成，要求参与者在回复首部确认任务 ID、版本、文件名和关键硬约束。上传和读取无法证明时，先补齐，不记为参加完整讨论。
2. 第一轮各自独立提出建议。主控先把自己的初始立场写入信息包，之后再读其他意见，降低跟随效应。要求所有模型区分事实、推断、未知、建议；指出最强反例、失败条件、成本和可验证的下一步，不要求迎合主控或 Pro。
3. 收集完整可见回答并保存来源、时间、状态；未完成回答不能截尾当成完整意见。下一版包保留原始可见回答，并附主控整理的分歧清单，不能只保留支持主控的部分。不要求或收集私有思维链，只保存可分享的论据与结论。
4. 至少完成两轮普通讨论：独立意见 → 阅读全部意见后的交叉批判与修订。重要分歧可继续一轮，不能无限机械循环。主控逐轮提交自己的修改意见，回答对其方案的质疑，并明确哪些观点被接受/拒绝及原因。
5. 对仍有影响决策的分歧，确定可核验问题；能在已授权范围做低成本只读核验就核验，否则写明未知。意见多不等于独立证据，不能按多数票宣称某方案有效。

### Pro 决策节点（合计最多三次）

- 普通参与者完成多轮讨论后，再给 Pro 上传含完整上下文、所有轮次意见、主控判断与未决问题的新版 .md；短提示要求集中裁决最关键的争议。
- 用途建议：第 1 次审查候选方案与核心争议；确有重大问题才第 2 次审查修订；第 3 次只用于最后关键裁决。不把普通澄清、附件可读性确认或闲聊额外发给 Pro 消耗回合；把要求一次写进同一条请求。
- 提交前核验 Chrome / “研究”项目内会话 / Pro / 文件附件；用 pro_budget.py reserve 为该完整 MD 预留一次额度，再点击发送。预留后发送结果不明也占额度，禁止自动重发。记录真正可见的发送与回复状态；不得把预留当作已发或已完成。
- 预留后的信息包保持只读；发送前确认实际附件仍对应预算簿中的文件版本、大小和 SHA。要改变问题或材料，先制作新完整版本，不在旧预留文件上静默修改。
- 每次 Pro 的完整可见意见加入下一版 .md，分发给全部普通参与者，主控也重新审视。若意见足够且无重大可证伪问题，直接收敛，不为用满额度再问。若有重大问题，普通模型先再讨论多轮，之后才考虑下一次 Pro。
- 若 Pro 与用户硬约束或已核实事实冲突，明确指出冲突，不能照做危险或未授权动作；有额度时带证据请其修订，没额度时由主控在用户约束内形成具名裁决或请求用户决定，不冒称得到 Pro 认可。

## 结束与交付

形成 final-decision.md：所选方案、淘汰理由、保留异议、事实/假设/未知、实现与验收步骤、预算和停止条件，以及“Pro 裁决 / 主控兜底 / 尚待用户决定”的准确状态。把最终完整信息包与决策发给普通参与者作知会；Pro 的知会可以省略，默认不为知会浪费一次额度。确实需要其再判断才申请剩余额度，不为知会突破三次限制。

向用户简洁报告结论、主要风险、Pro 使用次数及文件路径。讨论结束不等于实施授权；只继续用户明确授权的工作。任何角色都无权绕过隐私、平台认证、用户预算或输出范围。

## 工具与失败边界

上传和聊天使用已获准的 browser computer use；Pro 路由固定 Chrome。其他席位也优先按表中浏览器操作，不用内部子代理冒充外部网站模型。Shell 只用于本地信息包整理、大小/SHA、预算簿和测试，不能用来偷偷控制网页。

登录、验证码、附件不支持、配额不足或工具不可用时保留记录，告知用户具体阻塞；不换模型、不新建替身、不绕验证。恢复只读原状态，不自动重发不明消息。不声称本 skill 已完成真实跨站讨论；验收应区分文件/预算工具测试与实际网页运行。
