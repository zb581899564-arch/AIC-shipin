## 二、我发现的关键问题，按下一步收益优先级排序

### 1．最先修的不是模型，而是“用另一套推理算法给模型打开发分”

`temporal_sft8b_dev_v1/evaluate.py` 中，BASE 和 SFT 都用普通 greedy 生成；最终 `b_sft8b_package_v3/runtime.py` 却使用 `prefix_allowed_tokens_fn` 约束生成合法区间。生产协议自己也明确记载了这个差别。 

开发结果是：

| 开发臂 | 来源组宏 F1 | 解析情况 |
|---|---:|---|
| 未微调 8B | 0.342618 | 36 个窗口解析失败 |
| 微调 8B | 0.685003 | 112/112 窗口有效 |

**0.3424 的增量包含格式改善，不能全部解释成高光判断提高。**而提交链已经通过约束解码帮助模型满足格式，所以现在最缺的对照是：

> **相同输入、相同约束解码下，未微调 8B 和当前 37.63 的时间 LoRA，究竟差多少？**

这不是为了补论文消融，而是会直接影响下一步：如果两者差距很小，继续重复同样 SFT 的收益依据就明显变弱；如果约束后的原生 8B 反而更好，它本身就是一个值得生成完整包的候选。当前记录尚不能回答这个问题。

**执行建议：**新建一份“生产一致开发协议”，使用现有开放开发来源，不回写旧结果。至少比较当前 B 与原生 8B；已有 Mac adapter 则作为第三个完整配方加入。统一输出视频宏指标，来源组用于置信区间；同时单列格式有效率，不再让格式收益藏在语义收益里。

### 2．“只能选，不能不选”是真实实现问题，但不能拍脑袋决定它就是 12 分主因

当前四个位置一起锁死了非空：

- `temporal_common.py` 的提示词要求每窗 1–5 段。
- `sft_contract.py::segments_valid()` 拒绝空目标。
- `parse_segments()` 把空列表判失败。
- `BoundedSegmentsGrammar` 在列表开始后只允许继续打开一个区间，不允许直接闭合空列表。  

因此，**即使某个窗口没有值得保留的内容，当前生产算法也必须给它找出一段。**这与官方明确允许无明显高光视频输出空预测不同。[AICOMP](https://www.aicomp.cn/tracks/tracks-6/4267.html)

但这里不能做一个过于简单的“修复”：只把语法改成允许 `[]`，就宣称学会拒绝。现在训练全是已知正窗口，**模型缺乏什么时候应该不选的监督**。贸然放开空输出，也可能把原来的误选换成大量漏选。

更深一层，当前虽然没有把 UNKNOWN 显式写成 BCE 负标签，但区间 SFT 要求模型输出一份完整列表并结束响应，仍会让它学习教师的“选哪些、到哪里结束”的偏好。**没有显式负标签，不等于没有教师遗漏偏差。**

所以这项修正必须包含：**新的完整观察监督、训练目标、提示词、语法、解析器和合法空的合成测试**，不能只改其中一行。

### 3．空间端存在一个可直接构造反例的坐标解析错误

当前空间提示词已经要求 **0–1000 的整数坐标**，这点是对的。但 `inference/baseline_qwen3vl.py::parse_focus_norm()` 又对每个坐标分别猜单位：

```python
if value <= 1.5:
    norm = value
elif value <= 1000.0:
    norm = value / 1000.0
```

因此模型合法输出：

```json
{"center": [1, 500]}
```

按照提示词应解释为：

```text
[0.001, 0.5]
```

代码却会解释成：

```text
[1.0, 0.5]
```

**接近左边缘的位置，被解释到了最右边。**此外，解析器还接受从非 JSON 文本末尾提取数字，这使“最终框合法”不能等同于“坐标语义正确”。 

建议新版本只接受一种明确坐标合同：严格 JSON、恰好两个有限坐标、范围符合声明，统一除以 1000；不要逐坐标猜单位。无效输出进入有记录的重试或失败流程，不能悄悄猜成合法框。

**这是确定的代码缺陷，但出现频率尚未统计，不能声称修了就能涨几分。**先用非测试原始输出统计影响面，再决定是否形成修复包。

### 4．空间模型只学了“中心”，尺度自由度完全没有用

生产空间链调用 `predict_focus()` 得到中心，再由 `compute_crop_size()` 固定取最大合法裁剪尺寸。**模型没有决定裁剪宽度。** 

这值得认真诊断，不能继续用“旧框与新框很相似”推断空间已经很好。

一个直接的几何上界是：假设真实框与预测框长宽比相同，真实宽度为 \(w_g\)，当前固定最大宽度为 \(w_{\max}\)。即使中心完美，只要预测框更大，就有：

\[
\operatorname{IoU}\leq
\frac{\text{真实框面积}}{\text{预测框面积}}
=
\left(\frac{w_g}{w_{\max}}\right)^2.
\]

例如真实宽度是最大宽度的 80%，最好也只有 0.64。**这只是几何反例，不是在推断测试集真实尺度。**

下一步应在已有、身份和构图语义成立的非测试参考上，算一次：

**实际框 IoU → 最优中心但固定最大宽度的上界 → 允许尺度变化的参考上界。**

如果固定宽度本身限制很强，继续把锚点从 8 帧加密到 4 帧，甚至逐帧问中心，都不可能解决它。相反，如果固定尺度上界已经很好，就应先解决时间选择，不急着训练空间。

### 5．输入预算需要明确化，但别把已经修好的长度限制再当作故障

Linux 训练使用的 `min_pixels/max_pixels` 顶层设置，并不能直接证明视频每帧严格落在所写的像素预算内。当前生产协议已说明它继承的是实际 processor 默认视频预算；开发入口限制 8192 token，生产扩大到 16384。**工程上能生成，不代表这种实际输入分布差异已经经过质量比较。** 

这里不用另造一套方案：**Mac 迁移代码已经给出了更清楚的实现范式**——显式传视频 `size`，再从 `video_grid_thw` 检查实际处理后的每帧像素和总序列长度。这个合同可以在 Linux 复用，完全不需要依赖 MPS。

但我不建议因此马上把 Linux 一律降到 Mac 的 32768 像素。**明确预算是工程修正，选更低预算是质量取舍，二者要分开。**

### 6．时间候选的空间框并没有真正固定

`production.py` 先得到选中帧，再把选择间断视为新段，随后安排锚点。这意味着时间模型换一份选择结果，同一个源帧也可能落在另一组插值锚点之间。 

它未必使结果更差，但会污染归因。**新的非测试对照应先按源视频与镜头固定空间锚点，再让各时间方案读取同一份空间场。**旧 37.63 包保留原样；不能为方便比较改写历史包。

**止损出口：首个工作日仍无法形成有解释依据的正负监督，就不启动这次语义续训，先推进后文的低成本推理候选。**不会再让“补数据”把全部交付无限期扣住。

### 3．合法空要一次贯通，不留半条链

新版本应同时修改提示词、目标校验、生成语法、解析器、时间选择、全空情况下的空间调度和封包。

尤其要覆盖：**一个窗口为空、一个视频全空、整个批次没有空间请求**。当前空间推理存在要求锚点请求非空的检查；不能只让时间端返回 `[]`，随后在空间阶段因为没有锚点而失败。

## 五、怎么又快又好地评，而不是再花几天只出报告

### 开发评估分成三张表

**第一张：生产一致性。**同一输入合同、同一生成约束、同一时间映射、同一空间算法；记录合法空、解析失败、推理失败，不混为一个零分。

**第二张：模型质量。**旧标签上的结果叫“旧教师一致性”；新完整观察标签上的结果叫“新教师完整窗口一致性”；具备独立参考的部分单列。报告视频宏 P/R/F1、空误判、零交集、短事件与多段情况。当前代码已有视频宏指标，但主要决策基于来源组宏 F1；新协议应让官方对应的视频宏口径成为主要点估计，来源组负责成组重采样。

**第三张：成本。**时间推理、空间调用、解码、封包分别计时。不要把每次评估都变成完整空间重推：同一非测试空间场缓存一次，可以比较多个时间 checkpoint；变化了空间模型或算法，才失效重算。

**准入标准：**工程错误必须修；全选、全空或广泛退化停止该版本；弱结果不确定但机制明确，可以登记为风险候选进行官方整包验收。无需为每个候选跑五折，也不要求所有微小改进都先取得置信区间下界大于零。

### 本轮候选矩阵

保留 B=37.63 不动。其余最多形成以下五个有意义的新候选，不要求同一天全部生产：

| 候选 | 内容 | 为什么值得做 |
|---|---|---|
| **Z** | 原生 8B 时间＋与 B 相同的生产解码合同和 8B 空间链 | 排除原开发 BASE 解析失败造成的错误判断 |
| **M** | 已完成训练的 Mac adapter，按它自己的固定输入协议在 Linux 生产 | 利用已有投入，不再重做一次 MPS 训练 |
| **T** | 新完整监督下的 8B 时间续训，空间保留 | 本轮唯一优先训练成果 |
| **S** | B 的时间选择保持不变，只替换通过非测试门的空间方案 | 验证空间改进 |
| **TS** | 通过验收的 T＋S | 检查组合收益与交互，不预设增益相加 |

Mac 版本在仓库快照中完成了开发和 NONTEST8，尚无官方成绩；它是否已经交付或得分需要执行端先查现有记录，**不能把快照中的“正在推理”当成现在仍在运行**。

Z、T 若改变时间集合，空间锚点也必须处理前述依赖问题。新的离线比较共用源时间空间场；和旧 37.63 的线上比较，必要时明确是完整配方差异，不冒称纯时间消融。

官方确实允许每日最多五次，并取阶段最高有效成绩。**有五个合格、有不同依据的包就可以用五次；只有两个就用两个。**不每日重复旧包，也不根据总分连续二分阈值或逐视频探测。更高的有效整包都保留，不设虚构的“不到 0.2 分不算提升”。[AICOMP](https://www.aicomp.cn/notice/notice-3/5307.html)

## 六、Linux 和 Mac 怎么安排

### Linux：训练、评测、生产全部独立闭环

Linux 负责数据标注小试、唯一主训练、checkpoint 开发评估、完整空间推理及最终封包。继续用现有 GPU 作业锁，不抢占其他项目，不把历史空闲记录当当前可用资源。

**首先改掉资源控制的 Mac 心跳依赖。**当前 `controller.py::capacity()` 要求 Mac 的容量记录不超过 300 秒，等待超过 600 秒就停止 Linux 阶段。这是明确的运行依赖，不是抽象担忧。

新控制器应采用两机配额预留：

- Linux 有明确可用上限，可以在该上限内独立启动作业。
- Mac 离线时，仍保留其已知占用和已登记剩余任务的保守预留，**不能当作占用为零**。
- 两机加临时缓存的峰值仍不超过原 80 GiB；无法可靠界定 Mac 剩余写入时，不得冒险超分配。

这是改调度方式，不是取消磁盘红线。

### Mac：可中断的辅助，不再承担新 8B 主训练

Mac 可做代码检查、合成合同测试、非测试统计、CPU 评分、材料整理和已有 adapter 的归档。已经完成的 Mac 模型继续由 Linux 验收与生产；**不为了“Mac 不能闲着”再开一轮昂贵 MPS 适配。**

Mac 不在线，上述辅助任务可以暂停，Linux 主线不应受影响。也不要把 CUDA 和 MPS 拼成异构分布式训练来增加故障面。

新作业使用新目录和注册，保留历史源码、source lock 和失败证据；旧一次性 launcher 不直接重开。仓库运行说明本身也明确要求这一点。

## 最终决策

**我不会建议你现在重租卡、换更大的参赛模型，或者把 8B 原配方延长到十几轮。**

目前最有价值的三件事，顺序很明确：

**先把开发评估换成真实生产链，确认 37.63 的时间 LoRA 究竟比原生 8B 强在哪里；随后用新的完整观察监督训练“该选才选、可以不选”的 8B 时间模型；空间只在尺度上界诊断支持时升级。**

当前实现中，**非空限制、评测解码错位、坐标单位猜测、最大尺度锁死、Mac 心跳依赖**都有具体代码依据；但它们各自能贡献多少官方分还没有测量。冲 50 应靠一轮能改变监督质量和选模依据的实验，加少数完整候选的真实排序，而不是继续把同样的弱标签训得更熟。
